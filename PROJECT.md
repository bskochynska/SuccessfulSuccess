# spry

Monorepo with a FastAPI backend, a Next.js frontend and a Postgres database, started together by Docker Compose.

This document describes structure only: folders, what lives in each, and the contracts between parts.

**The only command a new developer runs:** `docker compose up`

## Pinned versions

| Component | Version |
| --- | --- |
| Backend base image | `python:3.12-slim` |
| Database image | `postgres:16-alpine` |
| Frontend base image | `node:20-slim` |

## Stack

| Part | Technology |
| --- | --- |
| Backend | FastAPI, SQLAlchemy (ORM), Alembic (migrations) |
| Frontend | Next.js (App Router), React, Tailwind, shadcn/ui |
| Database | PostgreSQL |

## Folders

### `/` (repository root)

Holds the two applications and the file that runs them together.

- `docker-compose.yml`: defines the three services (`postgres`, `backend`, `frontend`) and how they start. It is the single entry point for running the project.
- `PROJECT.md`: this document.

### `backend/`

The HTTP API and everything that touches the database. It is layered: a request flows `api → services → repositories → models`, and each layer only calls the one to its right.

- `Dockerfile`: builds the backend image from `python:3.12-slim`.
- `entrypoint.sh`: container start script. Applies all Alembic migrations, then starts the API server. A failed migration stops the container.
- `requirements.txt`: the backend's Python dependencies.
- `alembic.ini`: Alembic configuration; the database URL comes from the environment, not from this file.
- `alembic/`: migration environment.
  - `alembic/versions/`: one file per schema migration. The schema is changed only through migrations, never by hand.
- `app/`: the application package.
  - `main.py`: creates the FastAPI app, registers the routers and the CORS policy.
  - `config.py`: reads settings from environment variables (see the contracts below).
  - `db.py`: SQLAlchemy engine and session setup.
  - `api/`: HTTP layer. Route handlers only: parse the request, call a service, return the response. No business rules, no queries. First slice: the `meetings` routes and `/health`.
  - `services/`: business rules (for example, that a meeting must end after it starts). Called by `api/`; uses `repositories/` for storage.
  - `repositories/`: the only code that runs database queries. Called by `services/`.
  - `models/`: SQLAlchemy table definitions. Source of truth for the schema that Alembic migrates to.
  - `schemas/`: request and response shapes of the API. Source of truth for the HTTP contract.

### `frontend/`

The browser application. Next.js (App Router) with Tailwind for styling and shadcn/ui for components. TypeScript.

- `Dockerfile`: builds the frontend image from `node:20-slim`.
- `package.json`: frontend dependencies and scripts.
- `next.config.ts`: Next.js configuration.
- `components.json`: shadcn/ui configuration.
- `app/`: routes and layout (App Router). First slice: one page, `/`, which shows the list of meetings and the form to add a new meeting.
- `components/`: the application's own components (meeting list, meeting form).
- `components/ui/`: shadcn/ui primitives, generated by the shadcn tooling and not edited by hand.
- `lib/`: shared helpers. Includes the API client, which is the only code that calls the backend and mirrors the contract below.

## Services in `docker-compose.yml`

### `postgres`

- **Image:** `postgres:16-alpine`
- **Listens on:** `5432`, reachable from other compose services.
- **Depends on:** nothing.
- **Readiness:** healthcheck runs `pg_isready` against the configured database and user. Healthy when the server accepts connections.

### `backend`

- **Built from:** `backend/Dockerfile` (`python:3.12-slim`).
- **Listens on:** `8000`, published to the host as `8000`.
- **Depends on:** `postgres`, with condition `service_healthy`. It does not start until Postgres is healthy.
- **Startup behaviour:** `entrypoint.sh` applies migrations, then serves.
- **Readiness:** healthcheck performs an HTTP request to `GET /health` on port `8000` from inside the container, using only the Python standard library (the slim image has no `curl`). Healthy when it returns `200`. `/health` checks the database connection, so a healthy backend means the API and its database both work.

### `frontend`

- **Built from:** `frontend/Dockerfile` (`node:20-slim`).
- **Listens on:** `3000`, published to the host as `3000`. The app is opened at `http://localhost:3000`.
- **Depends on:** `backend`, with condition `service_healthy`. It does not start until the backend is healthy.
- **Readiness:** no healthcheck. Nothing depends on the frontend, so nothing needs to wait for it.

### Startup order

`postgres` (healthy) → `backend` (migrates, then healthy) → `frontend`

## Contracts between parts

### Environment variables

Values live in `docker-compose.yml`. There is no separate setup step for a new developer.

| Variable | Set on | Meaning |
| --- | --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `postgres` | Credentials and database name created on first start. |
| `DATABASE_URL` | `backend` | SQLAlchemy connection URL pointing at host `postgres`, port `5432`, using the credentials above. Used by the app and by Alembic. |
| `CORS_ORIGINS` | `backend` | Origins the API accepts browser requests from: `http://localhost:3000`. |
| `NEXT_PUBLIC_API_BASE_URL` | `frontend` | Base URL the browser uses to call the API: `http://localhost:8000`. |

### Frontend → backend

- The browser calls the backend directly, at `NEXT_PUBLIC_API_BASE_URL`. It uses the backend's published host port, not the compose service name `backend`, because the browser runs outside Docker.
- If the frontend or backend host port changes, `CORS_ORIGINS` and `NEXT_PUBLIC_API_BASE_URL` must be changed to match.
- All frontend code that calls the API lives in `frontend/lib/`.

### Backend → database

- The backend reaches Postgres only through SQLAlchemy using `DATABASE_URL`.
- The schema is created and changed only by Alembic migrations in `backend/alembic/versions/`.

### HTTP API (first slice)

All timestamps are ISO 8601 strings that include a UTC offset. They are stored as timestamps with time zone.

**Meeting object**

| Field | Type | Notes |
| --- | --- | --- |
| `id` | integer | Assigned by the server. |
| `title` | string | Non-empty. |
| `starts_at` | ISO 8601 string | |
| `ends_at` | ISO 8601 string | Must be later than `starts_at`. |
| `attendee_count` | integer | Zero or greater. |

#### `GET /api/meetings`

- Request body: none.
- Response `200`: JSON array of meeting objects, ordered by `starts_at` ascending. An empty list is `[]`.

```json
[{ "id": 1, "title": "Standup", "starts_at": "2026-01-15T09:00:00+00:00", "ends_at": "2026-01-15T09:15:00+00:00", "attendee_count": 6 }]
```

#### `POST /api/meetings`

- Request body: JSON object with `title`, `starts_at`, `ends_at`, `attendee_count`. `id` is not accepted.
- Response `201`: the created meeting object, same shape as one item of the list above.
- Response `422`: the body failed validation (missing field, wrong type, empty `title`, negative `attendee_count`, or `ends_at` not later than `starts_at`).

#### `GET /health`

- Response `200`: the process is up and the database answers. Used only by the backend healthcheck.

#### Error format

Every error response uses one envelope:

```json
{ "error": { "code": "validation_error", "message": "…", "details": [{ "field": "ends_at", "message": "…" }] } }
```

### Frontend page (first slice)

One page, no other routes. It contains:

- A list of meetings, loaded with `GET /api/meetings`.
- A form with the fields `title`, `starts_at`, `ends_at`, `attendee_count`, submitted with `POST /api/meetings`. After a successful submit the list is refreshed to include the new meeting.
